# Storage and structure audit

Run 2026-09-23 by thirteen agents with **read-only access to the live Postgres and Qdrant**, so
the numbers below are measurements of what we actually store, not estimates. Six lenses (stores,
relational schema, vector store, read path, representations, and what comparable systems do), each
adversarially verified, then a decider bound by one rule: evidence recall is already 0.991 and the
answerer is the bottleneck, so nothing may be cut for tidiness without an ablation that proves it
costs no accuracy.

## Verdict

The store count is right and is not where the problem is. Four stores plus OpenFGA is the correct topology: every one of them is load-bearing, and the two "obvious" consolidations (fold Qdrant into Postgres+pgvector; hand-roll ReBAC) are both refused on measured grounds below. Nothing should be cut at the store layer.

The design is not optimal in four precise places, only one of which is about storage:

(1) THE GRAPH HOP THROWS AWAY 42% OF THE FACTS IT CAN REACH. This is the finding that matters and no lens led with it. `neighborhood()` applies the SQL LIMIT (`limit=max_visited*3` = 600, postgres_store.py:432) and then dedups triples in Python afterwards (`first_of_each_triple`, postgres_store.py:151-164, called at :437). Duplicates therefore consume LIMIT slots. Measured on the bench hub entity `user:gina`: the query at its real limit returns 600 rows that collapse to 72 distinct triples, against 125 distinct triples reachable in the 658 rows that touch that entity. The mechanism is the tie-break: all 1,217 `mentions` edges are written at capped confidence 0.6 (native.py:335), so the second sort key — the neighbour's `mention_count` — decides, and the highest-mention entities are `Gina|240, user:gina|193, user:jon|191, Thanks|101, June|80, Shared|72, July|57, February|55`. One triple, `user:gina mentions Gina`, occupies 178 of the 600 slots. The LIMIT then truncates exactly the diverse tail. Compounding it, `_STRUCTURAL` at graph/retrieval.py:59 omits "mentions" while `_STRUCTURAL_PREDICATES` at graph/native.py:49-51 includes it — two near-identically-named sets disagreeing on the predicate that is 93% of the table — so those edges sort in the first ranking bucket and compete with typed facts for all 12 `graph_facts_max` slots. This is a recall defect wearing a storage defect's clothes, and it is the only thing in this audit that can touch the 39 failures.

(2) THE AUTHORIZATION CACHE IS INVALIDATED BY EXACTLY THE WRONG EVENTS. The scope cache key is a function of TENANT+USER(+AGENT) revisions (authz/service.py:71-73). Ordinary memory writes bump USER and TENANT on every consolidate (pipeline.py:471-477); measured on the bench tenant after ingest: `user|gina=216, user|jon=193` (409 bumps) and `tenant=321`, over 369 turns. Actual permission changes mostly bump nothing: `grant_thread` (authz/service.py:176) and `grant_document` (:195) write tuples and bump no revision at all; `grant_membership` (:236) bumps only when the caller passes an optional `revisions` argument (:276). So content churn destroys the cache constantly while grants can go stale for up to the 60 s TTL (constants.py:214) — which is the only backstop, and it is accidentally load-bearing. On every miss the resolve is 5 sequential `ListObjects` per subject (10 for an agent), a literal nested `for subject: for relation:` loop with no gather (scope.py:46-57).

(3) CONFIGURATION THAT CANNOT TAKE EFFECT. `ensure_collection` early-returns on a known name and only passes `on_disk_payload` inside its `if not exists` branch (qdrant_store.py:167-196), so indexer.py:96-101's `on_disk_payload=False` for memories has never applied: all 20 live collections report `on_disk_payload=True` and `quantization_config=null`. 18 of those 20 collections are retired embedding fingerprints holding 1,002 points, unreachable by any code path because every `drop_collection` caller names only the current fingerprint. And nothing prunes either queue: no DELETE on `OutboxRow` exists anywhere in repositories.py:758-827, and `remove_old_jobs`/`delete_old_jobs` appear nowhere in src/ — while seven periodic tasks are registered, including two retention jobs (`periodic.archive_purge`, `periodic.idempotency_purge`) that are the exact precedent nobody copied.

(4) THE HARNESS STRUCTURALLY CANNOT MEASURE TWO OF THE FOUR STORES. benchmark/env.py:108-112 forces `cache="memory"`, `authorization="memory"`, `blob="memory"`, `nli="lexical"` for every harness. No artifact on disk has ever exercised OpenFGA or Dragonfly. `locomo_judged_v5.json`'s "scope p99 318.7 ms" is a Postgres connection checkout plus one SELECT over a five-row table plus a dict get, on a box HANDOFF.md:23 already declares latency-contaminated (its encode p50 is 360.7 ms against a clean torch floor of 80.6 ms — roughly 4.5x inflated). That number is evidence of pool/CPU contention, not of store topology, and it must stop being quoted against the 300 ms budget in either direction.

Plus one latent data-loss hazard that outranks every cut here: `rebuild_search_index` drops the entire collection (`indexer.collection(base)`, reindex.py:61-65) but applies `--tenant` only to the rebuild (:72-80), and `collection_prefix` is a frozen constant with no override (constants.py:239, qdrant_store.py:164), so ~21 dev databases share two collections. `--drop --tenant acme` deletes bench_conv's 470 points — the corpus behind the 0.833. This is the command FREEZE-multilingual.md STEP 6 tells an operator to run.

## Target architecture

Same four stores plus OpenFGA. Nothing at the store layer changes. What changes is rows, invalidation keys, and two pieces of configuration that were written but never applied.

POSTGRES — three logical stores in one engine, all three earned.
- System of record (`memories`, 470 rows / 1,272 kB). Never read to answer a ranked query — candidate text comes from the Qdrant payload at engine.py:359 — and that is correct. It earns its place as the only thing a reindex can rebuild from (tools/reindex.py:71 selects on `temporal_status`/`deleted_at`), as the transactional truth for soft delete and supersession, and as the write side of the outbox's same-transaction guarantee. The context path does WRITE to it (buffered access bumps, builder.py:497-505), but off-request.
- Graph (`graph_relations` 1,314 rows / 1,448 kB, `graph_entities` 316 rows). Keep Postgres, per ADR-0010: the graph is derived state and one backup restores everything. What changes is the hop's sampling, not the store.
- Durable queue (`job_outbox` 734 rows, `observations` 369 rows) and the Procrastinate tables. `job_outbox` is what makes enqueue atomic with the business write inside one UnitOfWork; `observations` is what makes the 202 on POST honest. Both keep their existence and gain retention.
- OpenFGA's own tuples live in a database on the same server (5,388 tuples, 1 live store, 229 soft-deleted). That is deployment hygiene, not topology.

QDRANT — two collections, memories and knowledge, and the reason to keep it is not the vector index.
Measured: HNSW is doing nothing at this size. `segment.json` reports `"index": {"type": "plain"}` on every segment of every collection — no dense index has ever been built, because `indexing_threshold` is 10,000 KiB against 4,456 KiB of dense storage per segment. Exact scan and default params are indistinguishable (both under 2.3 ms across two independent lens measurements). So Qdrant is not here for ANN. It is here for the sparse leg: `Modifier.IDF` gives corpus-level BM25 inside the store (qdrant_store.py:181) and `FusionQuery(RRF)` fuses both legs server-side in one round trip (:332-360). Postgres offers `ts_rank`, not BM25 with corpus IDF, and the replacement would push RRF client-side under the GIL. Two collections, not one: engine.py:256-273 fans the per-kind searches out in one `asyncio.gather` so merging saves no round trip, and engine.py:275-277 interleaves by rank specifically so a long document list cannot crowd out memories — a property a single fused list destroys.
pgvector is refused on measured grounds, not preference: `pg_available_extensions` on postgres:16-alpine offers only `pg_trgm`, and that is not installed either. Adopting it is a base-image change plus the one reindex we have left, spent on plumbing, to replace a component whose server-side cost is single-digit milliseconds against a 20-80 ms encoder floor — and it would convert a measured 0.991 evidence recall into an unmeasured one.

DRAGONFLY — load-bearing for exactly one thing, an optimisation for everything else, and both halves are needed.
EPHEMERAL-lifetime memories live only here with no Postgres fallback (ephemeral.py:1-3; `recall` returns [] on CacheUnavailable at :48-55), so removing it deletes a documented API lifetime. Everything else degrades correctly: the bundle cache suppresses CacheUnavailable, the hot thread falls back to a Postgres read, idempotency's canonical row is in Postgres, the rate limiter fails open (middleware.py:174-179). It is also the only cross-instance rate-limit counter once WEB_CONCURRENCY=3 lands.
The pre-retrieval consolidation is already done and should not be re-litigated: `_lookup` (builder.py:227-280) reads the revisions once, derives both keys, and issues ONE `mget([scope_key, cache_key])`. Its docstring records that this was four round trips. The bundle SET is already off-path. Note the asymmetry that is correct: `bundle_id` folds in THREAD and GRAPH revisions, `authz_fp` deliberately does not — the bundle cache is rightly invalidated by content; the scope cache is wrongly invalidated by it.

OPENFGA — keep the service, fix the call pattern. The design already keeps it off the read path: `VisibilitySpecification.search_filter` (authz/visibility.py:127-133) is a pure local function of an AuthorizedScope, applied inside Qdrant and inside SQL. That is the cached local materialisation, and it works. The two things that make OpenFGA look like a per-request tax are both bugs: the inverted invalidation and an uncached `batch_check` on the conversation window path. Hand-rolling ReBAC as recursive CTEs to avoid a hop we would no longer be taking is a bad trade.

BLOB — filesystem provider, a compose volume rather than a service. Zero query-path round trips, 83 files / 540 kB in dev, 3 VERIFIED `archive_segments`. Costs one Literal in settings. Keep; fix its two broken read paths.

REPRESENTATIONS. Six artefacts per turn, and the amplification is real but the biggest one is also the best-evidenced.
- Verbatim OBSERVATION memories (353 of 470 rows, ~61 kB of 63 kB of memory content): KEEP, unconditionally. `locomo_verbatim_on.json` answer_recall 0.6309 / evidence_recall 0.9571 against `locomo_clean_off.json` 0.163 / 0.4022. Cutting it is a 4x accuracy regression, and it is the strongest ablation in the repository.
- Extracted typed facts (117 rows, 5.8 kB): keep. Cheapest thing in the system and the only carrier of subject/predicate/object.
- Dense + sparse vectors: keep both. `flag_off_dense.json` 0.7376 nDCG / 0.8714 recall vs 0.8451 / 0.9857 baseline; `flag_off_bm25.json` 0.8371 / 0.9571.
- Qdrant payload text: keep. It is a third copy of the string, and removing it converts every query into a 100-200 row Postgres fetch on the hot path to save sub-millisecond decode.
- `graph_relations.fact_text`: the verbatim-turn bloat is ALREADY FIXED at HEAD — `fact_text_for` (native.py:202-213) emits `<date> subject predicate object` and its own docstring records why. The 222 kB measured in the bench DB is pre-fix data (rows written 2026-09-22 17:02-17:07 UTC; fix a1b11b4 at 2026-09-23 01:56 IST). Nothing to decide; the bench corpus needs a regraph before any graph byte-count is quoted again.
- `graph_entities`: keep the table. `mention_count` is load-bearing for the deterministic tie-break — it is also what is currently poisoning the hop, but the fix is the extractor and the dedup point, not the column.

## Cut now - provably unread

### The 18 retired Qdrant collections (every name except mem_memories_st-granite-embedding-small-english-r2-torch-d384__bm25-v1-k1_2-b0_75 and its mem_knowledge_ twin), plus a sweep step added to the cutover procedure so the next fingerprint bump collects its predecessor.

- **Where:** Qdrant; add the sweep beside src/memory_service/tools/reindex.py:61-65. Inventory measured by me: `curl -s localhost:6333/collections` -> 20 names, then a GET per name.
- **Saves:** 1,002 points and ~16 MB across 18 collections, 36 segments the optimizer wakes for, and 18 names in every listing an operator reads. Each also holds a MutableRam sparse index in the Qdrant process on the 8 vCPU VM (RSS cost UNMEASURED).
- **Why safe:** Unreachable by construction, not by convention: the collection name is a function of the embedding+sparse fingerprint (indexer.py:73-85) and every drop_collection caller passes only indexer.collection(base). No running code can name a retired fingerprint. Seven of the 18 hold zero points. This is also the direct answer to 'do we need all this' — it is the clearest genuinely-dead storage in the system and needs no reindex and no judged run.

### Set on_disk_payload=False on the live memories collection by PATCH, and fix ensure_collection so the flag is reconciled on an existing collection rather than only at creation.

- **Where:** src/memory_service/adapters/search/qdrant_store.py:167-196 (the `if name in self._known: return` early exit and the `if not exists` branch that alone carries the flag); the intent is at src/memory_service/modules/rag/indexer.py:96-101.
- **Saves:** A page-cache read per returned hit at depth 100 on a remote Qdrant under memory pressure — which is precisely the target-VM condition and is not observable on this dev box. Payload is ~700-770 B/point, so a 5,340-point tenant is ~4 MB resident.
- **Why safe:** NOT blocked on the one reindex, contrary to three lenses. I verified the vendored client: `CollectionParamsDiff` carries `on_disk_payload: Optional[bool]` (.venv/.../qdrant_client/http/models/models.py:384-387), i.e. PATCH /collections/{name} sets it in place. Its own description also confirms indexed filter fields stay in RAM regardless, so the change affects text/attributes only, never tenant_id/visibility_keys/current. Free, reversible, no recreate.

### Fix `rebuild_search_index --drop` so the drop is scoped the way the rebuild is — refuse `--drop` together with `--tenant`, or delete by tenant filter instead of dropping the collection.

- **Where:** src/memory_service/tools/reindex.py:57 (the --tenant flag), :61-65 (the unconditional collection drop), :70-80 (the tenant-filtered rebuild); src/memory_service/config/constants.py:239 (`collection_prefix = "mem"`, no override) and adapters/search/qdrant_store.py:164.
- **Saves:** No bytes. It removes a data-loss path that is currently documented as an instruction.
- **Why safe:** Verified by reading the function: the drop names `indexer.collection(base)` and runs before any tenant predicate is applied. Because the prefix is a frozen constant, every one of the ~21 memory_* databases on this instance writes into the same two collections, so `--drop --tenant acme` destroys bench_conv's 470 points. This is the command FREEZE-multilingual.md STEP 6 hands an operator. Strictly a correctness fix — it removes capability nobody wants.

### Retention for the queue tables: register a periodic `remove_old_jobs` for succeeded Procrastinate jobs, and delete dispatched, non-dead job_outbox rows older than the CALLER'S idempotency window.

- **Where:** New periodic beside src/memory_service/modules/jobs/registry.py:206 (`periodic.archive_purge`) and :209 (`periodic.idempotency_purge`) — the precedent already exists. The missing DELETE belongs beside src/memory_service/adapters/db/repositories.py:758-827.
- **Saves:** Measured: ~20.8k succeeded Procrastinate jobs and 734 fully-dispatched outbox rows, against 3 memories in the compose database. At the observed ~2 outbox rows per ingested turn this is the only unbounded population in the system. Query cost is already bounded by the partial index, so this is storage and autovacuum pressure, not latency.
- **Why safe:** Verified: no DELETE on OutboxRow exists anywhere in repositories.py, and grep for remove_old_jobs/delete_old_jobs across src/ returns nothing. TWO CAVEATS THAT CHANGE THE PREDICATE, both of which one lens got wrong: (a) `add()` uses `on_conflict_do_nothing(index_elements=[OutboxRow.idempotency_key])` (repositories.py:770-776), so a dispatched row IS the enqueue-dedup record — retention must exceed the caller's idempotency window, not merely the relay's retry window; (b) `dispatched_at` is set AFTER handing the job to the broker (uow.py:74-85), so a dispatched row plus `observations.processed_at IS NULL` is the only evidence of a broker-lost job. Gate the delete on processed_at, keep `dead=true` rows, and do not sweep the 152 failed Procrastinate jobs before someone reads them.

### Stop writing the five Qdrant payload fields no reader can ever see: lifetime, temporal_status, representation, thread_id, importance.

- **Where:** Written at src/memory_service/modules/rag/indexer.py:333-352; excluded from PAYLOAD_FIELDS (ports/search.py:98-121), which is the only projection qdrant_store.py:46-47 ever applies. `current` sits next to them and must NOT be touched — it is both a filter and a payload index.
- **Saves:** ~12% of the measured 772 B/point payload. Nothing on the wire today (already projected out); it becomes resident RAM the moment on_disk_payload flips to False.
- **Why safe:** Two independent lenses did the full-scroll key census and the grep for payload readers. Stopping the WRITE is free now; removing them from existing points rides the reindex. Do it in the same change as the on_disk_payload flip so the RAM saving and the RAM cost land together.

### Delete the genuinely dead schema and service objects: `turn_run_links` and `message_versions` (insert-only, no SELECT anywhere in src), `graph_entities.summary` (a reader with no writer), `EntitySummaryService`, and the two API docstrings that falsely claim the pipeline writes ENTITY_SUMMARY and BELIEF. Apply migration 0008 to the lagging databases.

- **Where:** repositories.py:233 and :325 (the two inserts); adapters/graph/postgres_store.py:48 reads `r.summary` and graph/native.py's make_entity never assigns it (measured: 316 rows, all empty string); wiring.py:422-428 constructs ObservationPipeline with no `landing=`, so LandingReflection.on_landed is unreachable in every configuration (measured: 0 BELIEF, 0 ENTITY_SUMMARY rows, 0 rows carrying a 'landing' key); api/routers/v1/memory.py:88 and api/schemas/conversation.py:61 carry the false claim. `alembic_version` on the bench DB is 0007_tool_memory against an on-disk head of 0008.
- **Saves:** Little on this corpus; on a real conversational tenant `message_versions` is a second full copy of every edited message's content that no code will ever select.
- **Why safe:** Dead by construction and confirmed empty in data. ONE EXCEPTION I am overriding two lenses on: do NOT delete the `MemoryType.ENTITY_SUMMARY` / `BELIEF` enum members. They are published API enum values (DERIVED_MEMORY_TYPES, domain/memory.py:109) under a target that says every closed set is an enum; removing a member is a breaking API change during a freeze. Delete the service and fix the docstrings; version the enum later. Whether to WIRE LandingReflection is a Phase 4 accuracy decision (GAPS ranked item 5, the direct answer to the 14 partial lists) — the only thing due now is that the docs stop claiming it runs.

## Keep - things that look redundant and are not

- All four stores plus OpenFGA. This was the question asked and the answer is yes to every one. No store is propping up a redundant representation, and the two candidate consolidations are both refused on measured grounds, not taste.
- Qdrant — despite HNSW being measurably absent (`segment.json` reports `index.type: plain` on every segment of all 20 collections; no `vector_index-dense` directory exists anywhere). It is not kept for ANN. It is kept for `Modifier.IDF` giving corpus-level BM25 inside the store (qdrant_store.py:181) and `FusionQuery(RRF)` fusing both legs server-side in one round trip (:332-360). Postgres FTS gives ts_rank, not BM25 with corpus IDF, and the replacement pushes RRF client-side under the GIL. It also collides head-on with Phase 3, which plans a shared Unicode bm25-v2 tokeniser we control across six files.
- pgvector specifically — refused, and record it as considered-and-declined with the numbers. `pg_available_extensions` on postgres:16-alpine offers only pg_trgm, and that is not installed either, so it is a base-image change plus the one reindex we have left, spent on plumbing rather than on Phase 2+3 content, to replace a component whose server-side cost is single-digit milliseconds against a 20-80 ms encoder floor — and to convert a measured 0.991 evidence recall into an unmeasured one. If anyone reopens it, the gate is a pgvector HNSW run at 384-d on the same corpus reporting recall and p95 beside the Qdrant numbers, with the sparse leg replaced by tsvector/ts_rank_cd.
- OpenFGA — as a grant-time and scope-resolve dependency, not a per-request one. The `visibility_keys` design already means a read needs no OpenFGA at all: `VisibilitySpecification.search_filter` (authz/visibility.py:127-133) is a pure local function of an AuthorizedScope applied inside Qdrant and inside SQL. That cached local materialisation exists and works. Hand-rolling ReBAC as recursive CTEs to save a hop we would no longer be taking is correct for eighteen months and then silently is not.
- Dragonfly — EPHEMERAL-lifetime memories live only there with no Postgres fallback (ephemeral.py:1-3, :48-55), so removing it deletes a documented API lifetime; and it is the only cross-instance rate-limit counter once WEB_CONCURRENCY=3 lands. Everything else it does degrades correctly.
- `_lookup`'s single MGET (builder.py:227-280) — already consolidated from four round trips to one UoW + one `mget([scope_key, cache_key])`, with the bundle SET already off-path. Phase 2 step 5 is mostly LANDED; the honest residual is 1-2 round trips (hot-thread GET+LRANGE, ephemeral LRANGE), not the 4-to-2 one lens claimed. Do not re-do this work. Note the asymmetry is deliberate and correct: `bundle_id` folds in THREAD and GRAPH revisions, `authz_fp` does not.
- `job_outbox` — it looks redundant beside Procrastinate's own 21k-row queue and is not. It is what makes enqueue atomic with the business write inside one transaction (SqlUnitOfWork holds `self.outbox` beside every other repository), with OutboxRelay dispatching after commit and sweeping crashes. Only its retention is wrong.
- `observations` — a write-only inbox at query time, read once by primary key and never again, which looks like dead weight. It is the durable record that makes the 202 on POST honest and is what a crash between accept and process replays from. What is actually missing is the sweeper that would use it: `list_unprocessed` (repositories.py:639) has no production caller.
- Verbatim OBSERVATION memories — the single largest representation and the best-evidenced thing in the repository (`locomo_verbatim_on.json` 0.6309/0.9571 against `locomo_clean_off.json` 0.163/0.4022). Its design already avoids the obvious double-store: native.py:541 refuses to write one inside a thread or for an agent, and importance 0.25 vs 0.5 makes a parsed fact outrank the raw turn it came from.
- `memories.content` — a fourth copy of text Qdrant already serves, correctly OFF the query path, and not removable: it is the only source a reindex can rebuild from (tools/reindex.py:71).
- The Qdrant payload copy of the text — removing it to save sub-millisecond decode would convert every query into a 100-200 row Postgres fetch on the hot path. Strictly bad against a 300 ms budget.
- `visibility_keys` denormalised onto every row in both stores — the textbook duplication mistake, and measured nearly free where it runs: two independent lenses found server-side search cost roughly flat from 2 to 2,002 keys. It is what lets authorization run inside the store as one match-any instead of as a post-filter.
- The GraphStage prefetch, its 150 ms shielded budget (constants.py:320) and `max_parked_traversals=8` (:331) — the safety net that keeps a star-shaped graph's tail survivable without cancelling a statement holding a pooled connection. It becomes MORE important, not less, once the encoder drops.
- The payload projection itself (qdrant_store.py:46-47 over ports/search.py:98-121) — and specifically DO NOT act on ROADMAP-2026-09.md:277. That line says never return `tenant_id/visibility_keys/contributors/owner_principal/lifetime`. I verified the code is right and the roadmap is wrong: builder.py:139-155 copies `contributors`, `owner_principal`, `visibility` and `status` into `ContextItem.attributes`, and `tenant_id` is read at qdrant_store.py:412 to build every Candidate. ports/search.py:88-97 already documents this correctly. Fix the roadmap line; leave the projection alone. (A smaller real defect survives: `visibility`, `status`, `attributes`, `chunk_id` are projected but written on 0 of 5,340 points — four keys that cost a lookup and return nothing.)
- Chunks, document summaries, the ExpansionStage and the VerificationStage — all zero rows and ~zero milliseconds on the conversational corpus, which makes them look like dead weight in a LoCoMo-shaped audit. They are the document RAG product and the reason SciFact is measurable at all. Judging them on a corpus containing none of their inputs would be a category error.
- `ix_memories_expiring` and `ix_job_outbox_pending` — both read as dead (idx_scan=0) and both are scale insurance: correctly partial, zero-scan only because the planner seq-scans a 470-row and a 734-row table, and they flip at volume. More generally, treat the index-drop cut as the weakest item in this audit: I measured 5 never-scanned indexes on populated tables where one lens reported 7, and the counters drifted between lens runs because the auditors' own probe queries drove them.

## Latency effect

HONEST FRAME FIRST. No p99 for `/v1/context` exists anywhere on disk or in this audit, and I am not going to synthesise one by adding component timings. Two structural facts bound what anyone may claim: (a) benchmark/env.py:108-112 forces `authorization="memory"` and `cache="memory"` for every harness, so NO artifact has ever exercised OpenFGA or Dragonfly — every OpenFGA and Dragonfly number quoted across six lenses is out-of-band loopback curl, which I mark UNMEASURED-IN-SITU; (b) HANDOFF.md:23 declares `locomo_judged_v5.json` latency contaminated, and its encode p50 of 360.7 ms against a clean torch floor of 80.6 ms puts the whole file ~4.5x inflated. Its "scope p99 318.7 ms" is a Postgres checkout plus one SELECT over a five-row table plus a dict get. That is evidence for Phase 2 step 2 (WEB_CONCURRENCY) and against nothing else; it must stop being quoted as "already over the 300 ms budget."

p50: essentially unchanged by everything in this document. The encoder is the floor and none of these changes touch it. The graph sampling fix is a plan change inside a stage that is prefetched; the queue retention, dead collections and dead schema are off-path entirely; the on_disk_payload flip is invisible on a page-cached dev box. The only p50 item is the depth reduction, and it is gated elsewhere.

p99, in the order the changes matter:
1. Separating permission revisions from content revisions is the largest single p99 item, and it is an invalidation-rate change rather than a latency change. Measured: 409 USER bumps and 321 TENANT bumps over 369 ingested turns, against a 60 s TTL — so an actively-written tenant pays a cold scope resolve roughly every other request, and that resolve is 5 sequential ListObjects (10 for an agent). Fixing it converts the common case from resolve to cache hit. Do it by adding a MEMBERSHIP revision kind bumped from grant_thread/grant_document/grant_membership, keying the authz fingerprint on TENANT+MEMBERSHIP, and pairing it with a test that every grant_* bumps — because today the TTL is accidentally the only backstop and shortening it is not a substitute.
2. Gathering the 5 ListObjects instead of looping them collapses a serial chain to roughly its slowest member. Free, no blocker, and it bounds the residual cold-scope cost after (1). Bound the fan-out with a semaphore: 10 concurrent OpenFGA requests per cold scope at 20 rps can saturate the connection pool. While in that function, fix `sink.extend(x for x in found if x not in sink)` (scope.py:56) — an O(n²) list-membership merge under the GIL that a gather does nothing about.
3. The conversation window's uncached `authz.require` (conversation/service.py:305, reached from builder.py:538) is the only OpenFGA call that survives a warm scope cache, and it is serial after retrieval. REPLACE IT WITH A LOCAL ASSERTION — do not delete it. I verified the premise one lens offered for deleting it is false and the cut as written is an authorization bypass: `list_thread` (repositories.py:355-377) filters on tenant_id, thread_id, deleted_at and kind only — there is no visibility_keys clause, so `require` is the ONLY authorization on the window's content. The correct form is `assert thread_id in scope.thread_ids` against the already-resolved scope: same source of truth, zero round trips.
4. DO NOT move the encode ahead of the visibility resolve. This was proposed by two lenses and it is a net negative: `engine.py:215` passes the RESOLVED visibility into the graph prefetch starter, which today begins at t≈0 and completes under the encoder. Making visibility an awaitable delays the prefetch by the full resolve on the 37.5% of queries that route to graph. Fix the resolve's cost (items 1-2); do not reorder around it.

WHAT THE CRITICAL PATH BECOMES AT A ~20 ms ENCODER. The ordering changes qualitatively, and the reason is not the arithmetic — it is which steps hold the GIL. The encoder is the one hot step that runs OFF the event loop (SerialRunner thread, releases the GIL), which is exactly why the graph traversal, the collection check and the exact lookups are free today. Everything that replaces it as the constraint is GIL-held and therefore serialises across concurrent requests rather than overlapping:
 (i) the cold-scope authorization resolve, if items 1-2 do not land — it is now fully serial ahead of the encode (builder.py:357-364), where before Phase 2 it hid under it;
 (ii) qdrant-client payload deserialization — one lens measured ~19 ms of a 28 ms client-side search at depth 200 disappearing when the payload is dropped, and measured two concurrent searches at 49.6 ms against 56.6 ms sequential, i.e. a 12% overlap rather than 50%, because the conversion holds the GIL. This is the item the ROADMAP already names ("parsed under the GIL") and it is the strongest argument for the depth reduction;
 (iii) the encode itself, 20-27 ms;
 (iv) the conversation window — serial after retrieval, with a duplicate `threads.get` (builder.py:534 then conversation/service.py:302) and the uncached batch_check. Present on all real traffic and measured at 0.0 ms in every artifact, because every benchmark sends thread_id=None;
 (v) the graph traversal on graph-routed queries. Its measured "p99 10.2 ms" is doubly censored — bounded by the 150 ms shielded budget by construction, and recorded as the residual wait after a 360 ms encode finished. At a 20 ms encode it is exposed for the first time, and on expiry it drops facts silently rather than timing out (retrieval.py:218-224), so growth shows up as quality loss, not as an alert;
 (vi) the remaining assemble/serialise CPU, including the double serialisation on the miss path (`orjson.loads(model_dump_json())` at builder.py:805 then `orjson.dumps` at :345 — the route comment claims one pass and that is true only of a cache hit).
The consequence for sequencing: at a 20 ms encoder the binding constraint moves from a step that parallelises to a set of steps that do not, which makes Phase 2 step 2 (WEB_CONCURRENCY=3, three GILs) worth more to the 300 ms gate than every store change in this document combined.

ONE CORRECTION TO THE LENSES ON THE BUDGET: the DeBERTa NLI head is NOT inside the /v1/context budget, contrary to one verification's "missed" item. `modules/grounding/cascade.py` is reached from `/v1/grounding` and from an opt-in `answer` parameter on `/v1/retrieval` (api/routers/v1/grounding.py:163-186, retrieval.py:161). The `verify` stage in the timings is `VerificationStage` (context/evidence.py:211), which is CPU term-overlap, not entailment. It would become a second CPU model inside the same 8 vCPU if grounding were ever folded into the context path — which is a reason not to.

## Risks

- The graph ablation, run as HANDOFF Phase 4 step 6 currently specifies, will produce a FALSE NEGATIVE and retire 41% of the rows for the wrong reason. It would measure a hop that returns 72 of 125 reachable distinct triples with 178 of its 600 slots spent on 'Gina mentions Gina'. If that run comes back 'graph buys nothing', the honest reading is 'this sampler buys nothing'. Fix the LIMIT-before-dedup and the _STRUCTURAL divergence first, then ablate. This is the single sequencing risk that can destroy real capability on a measurement that looks clean.
- Removing the window's `authz.require` as one lens proposed is an authorization bypass, not a defence-in-depth trim. Verified: `list_thread` (repositories.py:355-377) has no visibility filter, so any caller supplying a thread_id in their own tenant would read that thread inside their /v1/context bundle. Ship the local scope assertion or ship nothing, and require a unit test proving a non-member still gets 403 on the context path.
- Raising the authz TTL without first making grants bump a revision is a stale-permission incident. Today `grant_thread` and `grant_document` bump nothing and `grant_membership` bumps only if the caller passes an optional argument — the 60 s TTL is the only thing that ever expires a revoked grant, and it survives today only because content writes keep clearing the cache by accident. Land MEMBERSHIP bumps and their tests in the same commit, or the cache-hit improvement is bought with a security regression.
- A Postgres-vs-Qdrant reconciler written against 'the' database would delete live vectors. The 4,740 'orphan' points are NOT production dual-write drift, contrary to the headline of one lens: ~21 memory_* databases share two collections because `collection_prefix` is a frozen constant, and in every internally consistent (database, tenant) pair the counts match EXACTLY (demo 3=3, bench_conv 470=470). Measured drift is zero. Build the reconciler as a per-database dry-run counter that must run clean across two consecutive passes before any delete arm ships, and fix the shared-prefix isolation first.
- Outbox retention keyed on `dispatched_at` alone breaks enqueue idempotency AND destroys the only evidence of a broker-lost job. `add()` dedups on `uq_job_outbox_idempotency` via on_conflict_do_nothing, and `dispatched_at` is stamped before the worker runs. Gate the delete on `observations.processed_at IS NOT NULL` and a window exceeding the caller's idempotency window.
- Every latency conclusion in this audit is about the miss path, and the hit rate of the bundle and scope caches at 20 rps is unknown — while the load harness's cold arm salts the query per request, which misses the BUNDLE cache but not the SCOPE cache, whose key is a function of context and revisions only. The arm labelled 'cold' may never exercise the expensive path the gate exists to bound.
- Every Qdrant number here comes from a 5,340-point collection with no HNSW graph and `full_scan_threshold=10000` (KiB), and every Postgres graph number from a 1,314-row table. The 'HNSW is irrelevant' and 'visibility_keys is flat in key count' findings are both properties of full scan, and both have a crossover nobody has located. The memories collection also has a plain keyword index on tenant_id rather than `is_tenant=true`, and no `payload_m`, so there is no per-tenant HNSW subgraph waiting on the other side of that crossover — that is the largest unpriced Qdrant risk and it is a reindex-class decision.
- The one remaining reindex is the real irreversibility and the cut list must be sorted by it. Sharing it: the on_disk_payload flip only if done by recreate (it need not be — PATCH works), the write-only payload field removal from existing points, and everything in FREEZE STEP 6. NOT sharing it: the graph changes (a re-ingest, a different and separately-budgeted operation), the ListObjects gather, the revision split, the window assertion, the queue retention, the dead collections, and the GIN index on graph_entities.aliases. Do not let graph work consume reindex budget it does not need.
- The bench corpus is not what the task premise says and not what HEAD writes. It holds 369 observations from ONE conversation and two speakers (jon 185, gina 184), not 788 turns from two; `temporal_status` is CURRENT on all 470 memories with zero soft deletes, so supersession and forgetting were never exercised; zero `messages` and zero `chunks` rows, so the conversation window, expansion, verification-escalation and knowledge arms of the read path have no data anywhere in this repository; and the graph rows predate a1b11b4, so every graph BYTE count is stale (the SHAPE — 1,314 rows, 351 triples, 1,217 mentions, two hubs — is not). Re-ingest at HEAD before quoting any graph size or per-turn ratio again.
- The remaining accuracy work is not in this audit and this audit should not be allowed to displace it. Evidence recall is 0.991 and 38 of 39 wrong answers already hold the gold turn; GAPS says two thirds of what is left is enumeration completeness and the answer protocol. Graph facts are ~12 lines of a ~23,700-character bundle whose memory count is pinned at 100 in 304 of 304 records. Of everything here, only the graph sampling fix can plausibly touch the 39 — and even that is a maybe. Cutting rows is worth doing for storage, ingest cost and comprehension; it should not be narrated to anyone as accuracy or p99 work.
