# Where the retrieval work stands — 2026-09-25

Written so another model, or a later session, can pick this up cold. Every number here was
measured in this repository unless it says otherwise. Where a number is contaminated or
projected it says so, because several hours were lost today to numbers that looked clean and
were not.

## 1. The one-paragraph version

Conversational retrieval is not recall-limited, it is COMPLETENESS-limited, and the loss is
in candidate generation rather than in ranking. On the full 1986-question LoCoMo set only
71.6% of answerable questions have ALL their gold evidence in the top 50 candidates, and for
multi_hop that falls to 32.6%. Selection - which of the retrieved candidates reach the block
the model reads first - costs a further 5.6 points overall. So retrieval loss is 5x selection
loss, and anything that only reorders what was already retrieved (a reranker, MMR) is working
on the smaller term. A reranker was measured end-to-end and made every metric slightly worse
at 6x the latency.

## 4. Fragmentation: a second, separate problem

    best SINGLE memory match       0.696
    union of the WHOLE bundle      0.9331
                                   ------
    present but carried by no one memory   23.7 points

Extraction is proposition-sized by design, so one gold turn becomes several memories and none
carries enough of it alone. This is NOT extraction losing information - the pieces are all
there - and no amount of reordering can fix it, because the retrieval unit is smaller than the
question's unit. `EvidenceRef.source_id` already links every memory to the turn it came from,
so the group is expressible today. `evidence_reconstructed` measures the ceiling that
reconstruction would reach; the run in flight produces the first value.

## 5. Decided order of work, with the evidence for it

1. **Candidate-seeded bridge expansion.** The only change that raises `cand@50`, and `cand@50`
   is where 28.4 of the 33.8 points of loss are. Our graph arm today starts from entities in
   the QUERY TEXT (`GraphStage._start` -> `self._query(ctx, routed, visibility)`) and runs
   PREFETCHED, i.e. concurrently with dense/BM25. A second hop by definition lives in a
   retrieved memory, not in the question, so the current shape cannot reach it. Traversal,
   visibility filtering, the time budget with shield/park semantics, `graph_budget_expired_total`
   and `routed.needs_graph` all already exist - the change is direction, not machinery.
2. **Coverage-aware selection.** Worth ~5.6 points overall and 6.7 on multi_hop - real, but a
   fifth of the retrieval term. Marginal-gain, not MMR: relevance-minus-redundancy still
   returns three phrasings of "London" and no "Acme". Every feature it needs (entities,
   source_id, timestamps, per-arm scores) is already on the candidate. No new storage.
3. **Make `QueryType` operational.** Ten categories are classified (`DOCUMENT_MULTI_HOP`,
   `TEMPORAL`, `ENTITY_RELATION`, `GLOBAL_SUMMARY`...) and all ten get identical treatment.
   The classification exists; the branches do not.
4. **Episode layer (L2).** We have L0 raw turn, L1 atomic proposition, L3 BELIEF /
   ENTITY_SUMMARY / SUMMARY / DERIVED. There is no L2: zero hits for "episode" anywhere. That
   is the layer GLOBAL_SUMMARY questions want. Only item needing a schema change; assignment
   should be deterministic first (entity, topic, temporal, thread continuity), not an LLM
   narrative.
5. Fielded / fact-augmented BM25 boosts. Cheap, smaller.

## 8. Traps this session actually fell into

- **Quoting two runs as one result.** 0.7993 accuracy and 307.8ms p99 came from DIFFERENT
  configurations (depth 100 and depth 50). Always check `k` and the git commit in provenance.
- **0.7993 blends two metrics**: 233 answerable graded for correctness, 71 adversarial graded
  by abstention rate. The correctness-only figure is `answer_recall_at_k` = 0.7983.
- **Order-blind metrics.** Six hours of ordering ablations were run against `evidence_ALL`,
  which flattens the bundle before scoring and therefore CANNOT move when only order changes.
  They also all carried `judged: false`. They proved nothing and were reported as null results.
- **Concurrency.** Three separate measurements were invalidated by running something else on
  the box. Load reached 119 once; the other benchmark made zero progress for 20 minutes.
- **`benchmark/` is in no test suite.** 645 unit + 197 integration tests passed green while
  every LoCoMo run aborted after 0 questions, because a caller in benchmark/locomo.py still
  passed a removed argument. Check benchmark/ by hand after any signature change.
- **The head cannot equal the bundle.** `render()` only emits the "Most relevant" block when it
  is SMALLER than the bundle. Setting MOST_RELEVANT_MAX to 50 with final_k=50 DELETES the
  block and leaves a bare chronological list - the arrangement already measured to make the
  model anchor on position and fail date arithmetic. 30 is the largest safe value.

## 11. RETRACTION - "source-turn reconstruction recovers a third of fragmentation" measured nothing

Section 10 reported this as a finding and built a plan on it. It is wrong, and the code audit
that found it was looking for something else.

``candidate_to_item`` builds every ContextItem's EvidenceRef with ``source_id=c.record_id``
(modules/context/builder.py:107). For a memory candidate that is the MEMORY's own id, not the
id of the turn it was extracted from. So:

  - ``GROUP_BY_SOURCE`` groups each memory with itself and nothing else, and has shipped as a
    no-op since dfe9832.
  - ``_evidence_reconstructed`` builds its groups by ``source_id`` (benchmark/locomo.py), so
    each group holds exactly one memory, and the "union of the memories sharing a source turn"
    is just that one memory.

Verified numerically against the shipped run rather than by reading alone. Over all 1982 rows
carrying ranks:

    max |evidence_reconstructed - (fraction of evidence_ranks that are not None)|  4.74e-05
    mean                                                                            9.63e-07

It is the same quantity, to rounding. And the two numbers that were set against each other are
the SAME measurement averaged two ways:

    0.7816   MACRO - mean over questions of the per-question found fraction
    0.6986   MICRO - found items / total items, pooled  (reported as 0.6960)

So the claimed 8.6-point recovery is the macro/micro gap of one quantity. Grouping contributed
exactly zero. ``benchmark/locomo.py`` even asserts in its own docstring that "Every memory
carries EvidenceRef.source_id back to the turn it came from" - true in the write path
(modules/memory/native.py sets it from ``observation.message_id``, and
adapters/db/memory_repository.py persists it) and false on the read path, because
adapters/.../indexer.py never writes it into the search payload and ports/search.py
PAYLOAD_FIELDS would not project it if it did.

WHAT IS RETRACTED
  - "source-turn reconstruction recovers 8.6 of the 23.7 fragmentation points"
  - "~15.1 points of evidence live in DIFFERENT turns"
  - "that demotes parent reconstruction from 'the fix' to 'a third of the fix'"
  - GROUP_BY_SOURCE's share of the dfe9832 gain: it did nothing, so whatever moved was
    COLLAPSE_SUBSUMED or noise

WHAT SURVIVES, because none of it depends on source_id
  - evidence_in_head 0.5968 -> 0.7231, and the head-widening projection it confirmed
  - complete_evidence_in_candidates@50 = 0.7188 and head@30 = 0.6654
  - evidence_ALL 0.9331, and the 6.7 / 21.4 split of the 28.1 points

WHAT THIS REVERSES
Parent reconstruction was demoted on the strength of a number that measured nothing, so it is
UNMEASURED, not weak - and the audit's second finding puts a real ceiling on it. Splitting the
432 rows that are incomplete at cand@50 by whether the gold is present in the render's union:

    203 of 432 (47.0%)   every gold item IS in the bundle, carried by no single memory
    229 of 432 (53.0%)   genuinely absent from the bundle

Reuniting a retrieved memory with its source-turn siblings therefore has a ceiling of

    complete_evidence_in_candidates@50   0.7188 -> 0.8503   (+13.2)
    multi_hop                            0.3333 -> 0.6135   (+28.0)
    open_domain                          0.4022 -> 0.6413   (+24.1)

That is an upper bound - ``evidence_min_overlap`` scores against the whole render including
graph facts, so token-bag coincidence inflates the 203 - and it needs the source_id plumbing
before any of it is reachable. But it says fragmentation may be a LARGER term than multi-hop
bridge retrieval, which is the opposite of the order the plan currently has.

The generalisable failure: a metric was trusted because it moved in a plausible direction,
and it had never been checked against the thing it claimed to measure. The same audit found
COLLAPSE_SUBSUMED and GROUP_BY_SOURCE shipped together, so a single combined delta was read
as evidence for both.

## 12. RETRACTION 2 - the +12.63 was the ruler moving, not retrieval improving

``benchmark/locomo.py:841`` scores each run with a head size it imports FROM THE SYSTEM UNDER
TEST:

    rank_metrics = _rank_metrics(evidence_ranks, _most_relevant_count(len(bundle.memories)))

``_most_relevant_count`` lives in ``domain/context_bundle.py`` and is derived from
``MOST_RELEVANT_MAX``. Raising that constant from 10 to 30 raised the metric's own head with
it, so the baseline was scored at head=10 and dfe9832 at head=30. Scored at a FIXED head, on
the same two result files:

    head      baseline    dfe9832     delta
      10        0.4848     0.4852    +0.0004
      20        0.5703     0.5728    +0.0025
      30        0.6207     0.6262    +0.0055
      50        0.6964     0.6986    +0.0021

    reported (each run at its own head)  0.5968 -> 0.7231   +0.1263

So the change bought at most +0.55 points, not +12.63. Putting three times as many memories in
the block called "the head" puts three times as much evidence in the head; that is arithmetic.
Whether a bigger head HELPS A READER is a different question and is still unmeasured - it is
exactly what the oracle-reader experiment exists to answer.

WHAT THIS RETRACTS: "the shipped gain", "the projection held", and the claim that dfe9832
delivered a large accuracy improvement. The projection (0.6602 -> measured 0.6654) was
arithmetic about rank distributions and was always going to hold; it was never independent
evidence.

## 15. The per-arm oracle failed, and the failure is the finding

Only one arm name appears anywhere in the run: ``fusion``, on 1386 of 1536 rows. The other 150
rows carry NO arm at all. ``graph`` and ``exact`` never appear.

    qdrant_store.py:395  retriever = "dense" if single.using == DENSE else "bm25"

is the single-query path; the fused path labels everything ``fusion``, so dense and BM25 are
indistinguishable downstream. That makes per-arm weighting and cross-arm agreement unbuildable
today, and it is why ``ContextItem.relevance`` is ~0.0016 for every ranked item.

More important: THE GRAPH ARM CONTRIBUTES ZERO MEMORY CANDIDATES. It expands by ``chunk_id``
only, while ``Relation.memory_id`` is written and read by nothing. So the multi-hop failure is
not that graph traversal is badly seeded - it is that graph traversal cannot return a memory at
all. Candidate-seeded bridge expansion would have been built on top of an arm that returns
nothing.

## 17. What the code audit found that neither plan had considered

78 of 95 findings survived adversarial verification. The ones that change the plan:

  - ``rrf_k`` is not sent to the store: Qdrant runs RRF at its default k=2, not the configured
    60. Every fusion number ever taken here used the wrong constant.
  - ``memories_max == final_k``, so the builder has zero headroom and ANY expansion memory is
    silently dropped. Sibling expansion, bridge expansion and path retrieval all measure as
    nulls until this is fixed. This is the true P0.
  - Source-turn sibling expansion's ceiling, recomputed at the repo's own threshold:
    cand@50 0.7188 -> 0.9355 (+21.7), multi_hop 0.3333 -> 0.8369. Larger than bridge expansion's.
  - ``_dedup`` is O(n^2) and re-normalises every kept text on every comparison: 9.6-26 ms per
    query, inside no timing stage, invisible in the p99 budget.
  - The graph route is most of the p99 breach: ~344.9 -> ~309 ms if its inflation is removed.
  - An episode layer sized honestly against open_domain is worth about +1 overall point, and a
    session-shaped episode MEASURES WORSE than today at k<=3. The roadmap has it too high.
  - Two adversarial questions carry real gold answers and are graded on abstention anyway.
  - The two metric families use different denominators (1540 vs 1536), so 0.9331 and 0.7188
    were never on the same base.

## 18. Competitive calibration - what our number is and is not

Our 0.7188 is complete-evidence RETRIEVAL. Hindsight 92.0, Mem0 92.5 and Mnemis 93.9 are
end-to-end LLM-judged ANSWER accuracy. Those are not the same measurement and must never be put
in one column. The one near-comparable public figure is Mem0's complete-retrieval@50 on
LongMemEval - 96.45% and 97.08% - and that is a different benchmark. MemORAI publishes LoCoMo
retrieval at Turn R@10 74.13% and Session R@10 92.28%, again a different definition.

The honest reading: single_hop 0.8395 and temporal 0.8318 are healthy. multi_hop 0.3333 is the
defect, and it now has a mechanical explanation rather than a tuning one - the graph arm cannot
return a memory.

## 19. The rule that would have caught all three artifacts

    No benchmark delta is accepted unless the metric's implementation is shown to be
    sensitive to the exact behaviour that commit changed.

Today produced three published numbers that were artifacts of the instrument, and this one
rule catches every one of them before it is reported:

  - ``evidence_ALL`` and ``answer_recall_at_k`` are computed over ``bundle.render()`` flattened
    into a token set. They cannot respond to ORDER. Six hours of ordering ablations were scored
    against them and read as null results.
  - ``evidence_reconstructed`` groups by ``EvidenceRef.source_id``, which on the read path is
    the memory's own id. It cannot respond to GROUPING. It was reported as an 8.6-point
    reconstruction gain.
  - ``evidence_in_head`` takes its head size from ``_most_relevant_count`` - imported from the
    module under test. It responds to the RULER as readily as to the system. A change worth
    +0.55 at any fixed head was published as +12.63.

The check is mechanical: before reporting a delta, construct two inputs that differ ONLY in the
behaviour the commit changed, and confirm the metric returns different values. If it cannot,
the metric is not evidence for that commit, whatever it reads.

## 20. Correction: Qdrant CAN take a configurable RRF k

I stated that parameterised RRF was impossible in this client. That was wrong, and checked
wrongly - I introspected ``FusionQuery`` (which has only ``fusion``) and stopped there.

    qdrant_client 1.19.0:  models.RrfQuery(rrf=models.Rrf(k=..., weights=[...]))
    server in compose:     qdrant/qdrant:v1.18.2          (parameterised RRF landed in 1.16)

Both ends support it. And ``Rrf`` carries ``weights`` as well as ``k`` - so PER-ARM WEIGHTING
is available server-side, which the code audit listed as unbuildable today.

What does NOT change: server-side fusion returns merged points, so the arm that produced each
one is still lost, and ``qdrant_store.py`` still labels them all ``"fusion"``. The two defects
are separable and only one of them is fixed by ``RrfQuery``.

The argument for fusing client-side is no longer layering, it is experiment cost. Retrieving
the arm lists once lets every fusion variant be scored OFFLINE from a single benchmark run:

    k = 2, 5, 20, 61   and   RRF vs DBSF      one run, re-fused in seconds
    against
    five full LoCoMo runs at ~45 minutes each

DBSF needs scores rather than ranks, which the client-side path has and the server-side path
discards - so the offline sweep is only possible on the arm lists.

And k must not be hard-coded to 60: Qdrant ranks from ZERO, so the conventional 1/(rank+60)
with one-based ranks corresponds to k=61 here. The current config says 60 and has never
reached the store, so there is no incumbent value to preserve - it is a free parameter and
should be swept, not assumed. Qdrant's own tuning work reports no universally optimal k, with
small k favoured on SciFact; conversational multi-hop has several relevant items per query,
which is the regime where a larger k is usually argued for. That is a hypothesis to measure,
not a default to adopt.
