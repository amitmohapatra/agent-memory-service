# The multilingual freeze

Decided 2026-09-23 by an eleven-agent pass over primary sources (model cards, papers, Hub file
listings, and this repository), each research lens adversarially verified. It supersedes Phase 3
of [ROADMAP-2026-09.md](ROADMAP-2026-09.md) wherever the two disagree, and it corrects that plan
in four places. Nothing here is a leaderboard screenshot: every number names its task set, and
anything not measured says so.

## The freeze

DENSE ENCODER — ibm-granite/granite-embedding-97m-multilingual-r2, runtime "onnx" (our own onnxruntime session, per ROADMAP-2026-09.md:23; never the sentence-transformers ONNX backend, whose optimum-onnx pins optimum~=2.1 and cannot coexist with sentence-transformers>=6 — verified: `grep -c optimum-onnx uv.lock` = 0), graph_file "onnx/model.onnx" (fp32, 390,004,608 B) as the SHIPPING DEFAULT, with onnx/model_quint8_avx2.onnx (98,247,878 B) promoted only if gate G1 passes. DECISIVE NUMBER: MTEB ML Retrieval (18 tasks) = 60.3, against an incumbent that appears in no multilingual retrieval table at any task count — https://huggingface.co/ibm-granite/granite-embedding-97m-multilingual-r2, row "granite-embedding-97m-multilingual-r2 | 97 | 384 | 60.3 | 50.1 | 60.4 | 65.5 | 24.9 | 52.2 | 2,534". Packaging verified at https://huggingface.co/api/models/ibm-granite/granite-embedding-97m-multilingual-r2?blobs=true : "gated": false, apache-2.0, 97,441,152 params, both ONNX files present. 384-d, so no schema change on top of the reindex.

WHY fp32 IS THE DEFAULT AND NOT int8 — this is a deliberate correction to ROADMAP-2026-09.md:340 and :520, which both name the int8 graph as the freeze. Our own measurement (docs/MEASUREMENTS.md:331-333) is that int8 is SLOWER than fp32 (p50 23.1–36.6 ms vs 19.5–27.3 ms) and lossier (min cosine 0.9667 vs 1.000000) on this box — and docs/MEASUREMENTS.md:147-149 records that the dev Docker VM has the AVX2 bit CLEAR even though the host i5-5257U has AVX2, so that result is a no-AVX2/no-VNNI result and says nothing about the target VM. fp32 is the graph whose vectors we have verified identical to torch. Ship it; promote int8 only on a VM number.

THE SWAP IS A VOCABULARY CHANGE, NOT A COMPUTE CHANGE — arithmetic on two files, not an assertion. Both configs are ModernBERT hidden_size 384 / num_hidden_layers 12 / intermediate_size 1536 / num_attention_heads 12 / local_attention 128 / global_attn_every_n_layers 3 (fetched config.json vs models/embedding-small/config.json on disk). Non-embedding params 12*(4*384^2 + 3*384*1536) = 28,311,552 for BOTH. Independent confirmation from graph bytes, computed here: IBM's fp32 graph 390,004,608 B minus our self-exported fp32 graph models/embedding-small/onnx/model.onnx 190,904,767 B = 199,099,841 B; the fp32 embedding-table delta (180,000 − 50,368) x 384 x 4 = 199,114,752 B. They agree to 14,911 bytes (0.0075%). The whole difference is a gather table. The residual latency risk is TOKENS PER QUERY (a 180,000-entry selected multilingual vocab tokenises English at a different rate than our 50,368-entry one), not layer depth — that is what G1 measures, and it is the only thing that can move E2.

POOLING NEEDS NO CODE CHANGE — verified on both sides. The candidate's 1_Pooling/config.json is pooling_mode_cls_token true, word_embedding_dimension 384; embeddings.py:348-365 reads that file and accepts exactly ["cls_token"] or ["mean_tokens"]. Note for the record: the incumbent's config.json says classifier_pooling "mean" while its 1_Pooling/config.json says cls_token true — our runner and sentence-transformers both follow 1_Pooling, which is why our ONNX/torch cosine is 1.000000. Do not "fix" that by reading config.json.

## What English costs

The published cost is 3.8 points of English retrieval: MTEB-v2 Retrieval (10 tasks) 53.9 for granite-embedding-small-english-r2 against 50.1 for granite-embedding-97m-multilingual-r2. Both sides verified verbatim: the incumbent's card row is "granite-embedding-small-english-r2 | 47 | 384 | 55.6 | 53.9 | 53.4 | 40.1 | 61.9 | 75.51 | 48.9 | 199" under the header "AVERAGE | MTEB-v2 Retrieval (10) | CoIR (10) | MLDR (En) | LongEmbed (6) | Table IR (5) | MTRAG (4) | Encoding Speed (docs/sec)" (https://huggingface.co/ibm-granite/granite-embedding-small-english-r2); the candidate's is the 50.1 in the "MTEB Retrieval (eng, v2) (10)" column quoted above. Same task set name, same task count, so the comparison is legal in kind.

MARK IT AN ESTIMATE, NOT A MEASURED DELTA. The two numbers come from two different model cards and were not produced in one evaluation run — the candidate's own card disagrees with its own paper on two other columns of the same row (LongEmbed 65.5 on the card vs 62.9 in Table 5; Code 60.4 vs 60.5), and the incumbent has no row in that Table 5 at all. Treat −3.8 as a plausible published estimate of direction and magnitude, never as a prediction for our corpus. Also do not quote the two throughput figures against each other (199 docs/s for the 47M model, 2,534 for the 97M): both cards state the same protocol — "on a single H100 GPU using a sliding window with 512 context length chunks" — so a 12x inversion between them means one of the two published numbers is wrong. Neither is a CPU number, and no vendor in this field publishes one.

HOW IT IS GATED — on our task set, not on MTEB. The binding gate is SciFact-1000 through our own ingestion path: `make bench-external` must hold ndcg_at_10 >= 0.825 against the 0.8451 rerank-off reference (a −2-point tolerance) and recall_at_10 >= 0.97, exactly as ROADMAP-2026-09.md:338 already writes it. Second gate on the conversational path: LoCoMo evidence recall must stay >= 0.987 (it is 0.991 at HEAD, docs/GAPS-2026-09.md), and the 2-conversation judged strict must not fall below v5's 0.833. If SciFact fails, the freeze reverts to granite-embedding-small-english-r2 and the English-vs-multilingual trade goes to the owner with both numbers — which is what the roadmap already commits to, and it is the right commitment.

ONE HONEST FOOTNOTE FOR THE LEADERSHIP BRIEF: the candidate's published MIRACL English is 45.39, the lowest English of the four granite models in the paper's Table 11. So the English regression may also show up per-language inside the multilingual harness, and it should be read there as well as on SciFact rather than being allowed to hide inside a multilingual average.

## Risks

- THE GRAPH CHOICE IS INSIDE THE COLLECTION FINGERPRINT, so 'ship fp32 now, promote int8 after the VM measurement' costs a SECOND reindex. embeddings.py:383-391 puts the graph file name in the vector-space name, deliberately and correctly ('the int8 graph sits at min cosine 0.9667 from the torch runner where the fp32 graph sits at 1.000000, and two collections that disagree by that much must not share a name'). This is the single most important sequencing fact in the freeze and it appears in no lens. If G1 cannot be run before the reindex, the honest choice is fp32 and a written decision not to revisit it this cycle.
- Tokens per query is the only live threat to E2 and it is unmeasured. The FLOPs case is settled by arithmetic (28,311,552 non-embedding params both ways; the 199,099,841-byte graph delta matches the 199,114,752-byte embedding-table delta to 0.0075%), but per-token cost times an unknown token count is still unknown. The candidate's vocabulary is described by its own paper's abstract as SELECTED (the model is 'built via model pruning and vocabulary selection'), so English coverage under a 180,000-entry multilingual vocab is not guaranteed to match a 50,368-entry English one. STEP 1 falsifies or confirms this for free, before the VM exists.
- No CPU latency number exists anywhere in this field, for any candidate. Every vendor figure is H100 throughput (2,534 and 199 docs/s, and those two contradict each other by 12x under an identically-worded protocol). ROADMAP-2026-09.md:15 and :377 already say 'no CPU-latency comparator exists publicly, so we publish ours' — this pass confirms it. Every latency statement about the candidate, including mine, is arithmetic until G1 runs.
- The English retrieval cost is an estimate across two model cards, not a measured delta, and the candidate's card disagrees with its own paper on two other columns of the same row. If SciFact comes in below 0.825, the freeze reverts and the multilingual target slips — plan for that outcome rather than treating the gate as a formality.
- The NLI swap has a published ENGLISH REGRESSION that the roadmap never priced: MNLI-m 0.857 vs 0.903, ANLI-all 0.537 vs 0.579, FEVER 0.761 vs 0.777. Our only English grounding artifact (benchmark/results/grounding_gate.json) scores 42/42 with borderline tp=fp=fn=0 and provenance.git_commit 'unknown' on a 4-core box, so it has no power to detect a 4.6-point drop and fails ROADMAP-2026-09.md:93's own provenance rule. We would be swapping a measured English capability for an unmeasured non-English one with no instrument that can see either.
- The multilingual claim is broader than the tokenizer. Nineteen English rule lexicons in native.py, the English query router (router.py), English hedge/discourse lists in cascade.py and ~200 English patterns in document_facts.py are all out of scope by design — so the freeze must state plainly what 'multilingual' means: dense retrieval, sparse retrieval, entailment and verbatim retention, NOT rule extraction, routing or document fact extraction. Saying otherwise to leadership is the reputational risk, not the code.
- CROSS-LINGUAL (query language != memory language) is a different property from multilingual and the candidate publishes NOTHING on it — its paper names MLQA in the evaluation-dataset list and gives no table. Every published pair matching our scenario is large and asymmetric, with English-query-to-non-English-memory the worst cell. The Phase-3 gate as written (per-language recall@10) cannot see it. GAPS-2026-09.md:65 already calls for a cross-lingual row; it must be added or 'multilingual' is claimed on a monolingual measurement.
- The sparse leg's cross-lingual contribution is probably small even after bm25-v2. The fusion delta on a cross-lingual set is +0.4 recall@100 (M3-All 75.5 vs M3-Dense 75.1, BGE-M3 Table 2) and +0.2 recall@20 for mGTE. Frame bm25-v2 to leadership as 'non-Latin input stops being silently dropped', which is a correctness defect with a verified reproduction, NOT as 'cross-lingual retrieval improved'.
- The reindex is shared with Phase 2 and Phase 2 merges first (HANDOFF.md:47, and the merge order encoder->wire->datapath->render). If the encoder fails its gate AFTER Phase 2's reindex has landed, the one shot is spent. The model choice was priced by every lens; the sequencing is the actual irreversibility.
