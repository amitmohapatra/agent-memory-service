# Audit 2026-09-23: 50 confirmed findings

Six read-only dimensions (API surface, configuration openness, `/v1/context` hot path, ingest
path, dead code, SOLID/layering) over 61 agents. Every candidate was handed to a separate agent
instructed to **refute** it; 55 were raised and 50 survived. The five that did not are not listed,
which is the point of recording the method: what follows is what a hostile reader could not talk
down, not what a finder proposed.

Findings already fixed are struck through: the group-id trust boundary and the unscoped job read
(`ca50f7d`), and the dedup batch (`5d75fbb`). Everything else is open.

## HIGH (13)

### ~~Body-supplied scope.group_ids are merged into the authorized scope and become read keys~~

`src/memory_service/api/deps.py:95` · api-surface

Any caller that reaches /v1/recall, /v1/context, /v1/graph/query or any body route with valid
headers can read every GROUP-visibility memory, chunk and message in the tenant by listing group
ids in `scope.group_ids` — no OpenFGA membership is ever checked for them. The end user of an SDK-
driven app controls the body, so this is an in-tenant cross-group data leak through the documented
request model. Note tests/unit/test_api_context.py:52 currently asserts the union
(`body["group_ids"] == ["finance", "legal", "ops"]` for a body carrying "ops"), so the test
encodes the behaviour and must change with the fix. The same shape applies to `agent_group_id` /
`agent_run_id`, which scope.py:79-80 copies from the body into `agroup:` and `run:` keys with no
grant check.

### include_internal=true returns INTERNAL messages that GET /v1/messages/{id} refuses to the same principal

`src/memory_service/api/routers/v1/conversation.py:159` · api-surface

Any principal with thread read access can list the planner/agent/tool INTERNAL messages of that
thread — the exact records the per-message route denies it. A caller that gets 403 on GET
/v1/messages/{id} gets the same content by calling GET
/v1/threads/{id}/messages?include_internal=true. The parameter's documented constraint is enforced
nowhere.

### models.embedding.threads is the only encoder knob and it is silently overwritten at startup by the NLI loader

`src/memory_service/config/settings.py:162` · config-openness

MEMORY__MODELS__EMBEDDING__THREADS has no effect on the dense encoder in any process where the NLI
model loads (i.e. every normal API and worker process): the NLI loader resets the process-wide
intra-op count to the frozen 2 immediately after the encoder set it. The one env knob over the
component that is 61% of query p99 is inert, and both .env.example:116-118 ("torch intra-op
threads for the frozen embedding model; unset means torch's own default (every core)") and
settings.py:159-160 describe behaviour the code does not have — unset actually yields 2
(wiring.py:282 falls back to dense.threads), and set yields 2 as well. An operator tuning latency
here measures no change and concludes the encoder is not thread-bound.

### The production guard fires only on environment=prod, so staging accepts trusted_dev auth with the hardcoded 'dev-key'

`src/memory_service/config/settings.py:266` · config-openness

A deployment set to MEMORY__SERVICE__ENVIRONMENT=staging starts with header-trust authentication
and a single API key whose value is the literal default in settings.py:128 and is printed in
.env.example:70. Anyone who can reach the port and has read the repo can authenticate as any
tenant/user by setting three headers. The operator has been told by the shipped .env.example that
staging refuses exactly this, so the misconfiguration is invisible: the service starts clean and
/health/ready is green.

### openfga_store_id/openfga_model_id default to None and are never required, so each process auto-creates its own OpenFGA store through an unguarded check-then-create race

`src/memory_service/config/settings.py:135` · config-openness

On a fresh `docker compose up`, up to four processes can simultaneously find no store named
'memory-service' and each create one. Authorization tuples written by the worker land in one store
while a check served by an API worker reads another, so the same request is allowed or denied
depending on which process handles it — a silent, non-reproducible authorization split with no
error anywhere. Even without the race, the authorization store is auto-provisioned rather than
pinned, so a restart against a wiped OpenFGA database silently starts from an empty tuple set
instead of failing.

### Evidence escalation adds an unbounded number of full-text chunk candidates to the hot path

`src/memory_service/modules/context/evidence.py:393` · context-hotpath

One `see Section 8` cross-reference whose companion is missing pulls every chunk of that section's
subtree (a 5-subsection x 4-paragraph section is ~26 nodes, ~26-50 KB of chunk text) into
`result.candidates`. They all survive `_cap_evidence` because it only counts items with
`expansion_edge is None` (engine.py:537-542), so the ranked-depth knob does not bound them. Every
one of them then pays a `candidate_to_item()` ContextItem + EvidenceRef construction in
builder.py:577 and an `UnusedEvidence` carrying the full text in builder.py:712-716 — for a bundle
that can place at most `knowledge_max=12` of them and keeps only `UNUSED_MAX=8` unused entries.
Request latency and peak memory scale with document structure rather than with any configured
budget.

### Clause-by-clause LLM calls in extract(): up to 16 sequential model round trips per observation

`src/memory_service/modules/memory/native.py:492` · ingest-path

Every observation in memory.process_observation can issue up to 16 gateway round trips strictly
one after another, each for a single clause, with no data dependency between iterations (the only
shared state is the two integer budgets and the `seen` hash set, both resolvable after the fact).
At a typical flash-model latency this serialises into tens of seconds of wall clock per
observation and caps ingest throughput at roughly one observation per (16 x model RTT). The repo
already contains the fix shape one directory away: chunking.situate_chunks packs 8 chunks into a
single structured() call with an index-keyed JSON reply (chunking.py:356-373) -- the same packing
applies here, or the clauses can simply be gathered.

### ~~Dedup loop embeds each candidate memory one at a time with embed_query instead of one batched embed_documents~~

`src/memory_service/modules/memory/native.py:1070` · ingest-path

For each extracted candidate, every existing memory whose lexical similarity falls in [0.5, 0.92)
costs its own single-text encoder round trip, issued sequentially -- up to 20 per candidate, and
the pipeline walks candidates sequentially too (pipeline.py:305 `for cand in candidates:` ->
pipeline.py:323 `await self.provider.consolidate(...)`). The dense encoder is the single most
expensive component in the system; here it is driven at batch size 1. Collecting the loop's
`mem.content` values and issuing one embed_documents call before the loop turns N sequential
encoder calls into one, without changing any decision the loop makes.

### index_document reads the document's entire chunk set twice, and the 5000-row cap silently drops the tail of large documents

`src/memory_service/modules/rag/indexer.py:139` · ingest-path

Two effects. (1) Every non-forced index job transfers and materialises every chunk row of the
document twice -- text plus contextual_text are the largest columns in the table -- doubling both
Postgres traffic and the peak RSS of the embedding worker, for a filter that is one list
comprehension over data already in hand. (2) Past 5000 chunks the cap is silent: list_chunks
returns the first 5000 by (node_id, ordinal), _index_chunks indexes only those,
mark_chunks_indexed marks only those, and document.index is enqueued exactly once per parse
(ingestion/service.py:324-337), so chunks 5001+ are never embedded and never searchable;
`keep={c.chunk_id for c in all_chunks}` at indexer.py:177 is built from the same truncated list,
so _purge_superseded also has no idea they exist. A chunked/paged read over the chunk table fixes
both.

### AdmissionGate and LandingReflection are never wired: the admission gate, beliefs and entity summaries never run

`src/memory_service/adapters/wiring.py:423` · ingest-path

In the running service, every extracted candidate bypasses admission entirely (nothing is ever
DEFERred or rejected), and the whole landing pass is dead: no strengthen/weaken/supersede of
related memories, no BELIEF memories, no ENTITY_SUMMARY memories. The API contract advertises the
opposite to callers -- "the pipeline itself writes ENTITY_SUMMARY, OBSERVATION, BELIEF, TOOL,
AGENT, TASK and USER" (api/routers/v1/memory.py:88) -- so two of the seven promised memory types
can never appear. ~500 lines across landing.py, derived.py and admission.py are shipped but
unreachable, and any measurement attributed to them is measuring code that did not execute.

### The whole relation-invalidation pathway is unreachable: port method, both adapter implementations, the edge builder and its three reason constants have zero callers

`src/memory_service/ports/intelligence.py:232` · dead-code

~100 lines of shipped code that can never execute, and a capability the docs claim exists does
not. docs/TARGET_STACK.md:79 lists "invalidation edges instead of deletion" as a delivered
consolidation feature and modules/graph/invalidation.py:1-11 documents an INVALIDATED status
meaning "it was never right"; no row ever gets that status, so no `invalidated_by` audit edge
(domain/graph.py:23 INVALIDATED_BY) is ever written, and the `include_invalidated` flag plus the
`status NOT IN ('RETRACTED','INVALIDATED')` filters at postgres_store.py:95 and :515 can never
exclude a single row. Anyone extending this (e.g. wiring re-extraction or contradiction handling)
will also have to notice that the helper signature, both adapters and the reason vocabulary have
never been exercised by a test or a call site.

### Task names are defined twice, once by the enqueuer and once by the registrar, and the guard test cannot see the drift

`src/memory_service/modules/conversation/service.py:37` · solid-coupling

Renaming a task in one file and missing the other produces no test failure. At runtime
ProcrastinateTaskQueue.enqueue raises `KeyError: task ... is not registered`
(adapters/tasks/procrastinate_queue.py:150-152); OutboxRelay._dispatch catches it, marks the row
failed and retries until dead at 20 attempts (adapters/db/uow.py:73-84). Every affected write is
answered 202 and silently never becomes a memory — the exact incident documented in
jobs/registry.py:31-36 and in the test's own docstring.

### ~~GET /v1/jobs/{job_id} returns any tenant's job metadata because the TaskQueue port has no tenant concept~~

`src/memory_service/api/routers/v1/conversation.py:300` · solid-coupling

Procrastinate job ids are sequential integers, so any authenticated tenant can enumerate ids and
read other tenants' job task_name, queue, status, attempts and scheduled_at — the existence and
kind of another tenant's ingestion and memory work. Tenant isolation is enforced everywhere else
in the service through visibility keys and AuthorizedScope; this one path has no scoping because

## MEDIUM (25)

### hints.memory_type=CUSTOM without custom_type is accepted with 202, then destroys the whole observation job

`src/memory_service/api/schemas/conversation.py:69` · api-surface

POST /v1/observations (or /v1/messages) with `{"hints": {"memory_type": "CUSTOM"}}` returns 202
"durably acknowledged" and then the job raises inside MemoryPipeline.run before
`uow.observations.mark_processed` (pipeline.py:251), so the observation is never marked processed
and EVERY candidate extracted from it is lost, not just the CUSTOM one — the job retries and fails
again on each attempt. This is exactly the failure ProcessingHints' own comment
(domain/observation.py:29-31) says was fixed: "every observation hinted CUSTOM produced a failed
job and no memory, silently". A two-field model_validator on ProcessingHintsIn would make it a
422.

### RecallRequest.kinds accepts "summary" but the route strips it before retrieval, so the search runs over nothing

`src/memory_service/api/routers/v1/retrieval.py:250` · api-surface

POST /v1/recall with `kinds: ["summary"]` passes an empty tuple to retrieve(); unless the router
happens to classify the query as GLOBAL_SUMMARY, no store round trip is made at all and the caller
gets `results: []` with a 200 — a documented, validated input that silently returns nothing. With
`kinds: ["chunk","memory","summary"]` summaries are likewise never searched, so the field cannot
do what its description promises.

### PlanRequest.available_tools has no upper bound and costs one DB round trip per element inside the request transaction

`src/memory_service/api/routers/v1/tools.py:155` · api-surface

One POST /v1/tools/plan can force hundreds of thousands of sequential SELECT/INSERT round trips in
a single open transaction: the 25 MB body cap divided by a ~12-byte `{"name":"a"}` element is ~2M
entries. That is an unbounded single-request hold on a pooled DB connection and on the worker's
event loop on a service targeting p99 < 300 ms; it also lets one caller write unbounded rows into
the tool registry.

### GraphQueryRequest.entities is unbounded and reaches an IN-list query with no row limit

`src/memory_service/api/routers/v1/graph.py:33` · api-surface

A single POST /v1/graph/query can send a name list large enough to build a multi-megabyte IN
clause plus a JSONB `?|` array predicate over the entity table, and the result set itself is
unlimited (every matching entity row is materialised and converted). The route's careful
hops/max_visited caps are bypassed because the cost lands in entity resolution, before the bounded
traversal.

### Unbounded request strings and ints land in fixed-width columns, producing 500s instead of 422s

`src/memory_service/api/schemas/conversation.py:121` · api-surface

Each of these turns caller input into a PostgreSQL DataError (22001 value-too-long / bigint out of
range) that the generic handler renders as `{"code": "INTERNAL", "retryable": false}` with a 500
and a logged stack trace (api/errors.py:162-171) — a client error reported as a server error, and
it pollutes the 5xx rate the release gate reads. The thread_id case additionally lets a caller
create threads whose ids violate the id contract the rest of the system assumes (prefixed ULIDs,
tenant-prefixed FGA object ids).

### The 25 MB body cap is enforced only when the client sends Content-Length

`src/memory_service/api/middleware.py:66` · api-surface

A chunked upload bypasses the only size gate in front of the service: Starlette spools the part to
a temp file (unbounded disk) and `await file.read()` then loads all of it into the worker's memory
before the 100 MB ingestion check can reject it. Same for JSON routes, where the body is fully
parsed before any model validation. One client can drive a worker to OOM during a run at the
target rate.

### Idempotency-Key header is taken verbatim into a VARCHAR(300) primary key

`src/memory_service/api/middleware.py:64` · api-surface

Any POST with an Idempotency-Key longer than 300 characters (headers are accepted up to several
KB) fails the INSERT with a Postgres 22001 and is returned as a 500 INTERNAL, non-retryable,
instead of a 422 — and the write itself is lost. The header is documented in the OpenAPI
description (api/openapi.py:37) with no stated bound.

### models.llm.model / fast_model are free-form env-settable strings; a wrong value is never validated and degrades the service silently

`src/memory_service/config/settings.py:197` · config-openness

A typo or a stale model name in .env produces a service that starts cleanly, reports "llm":
"bifrost" on /version, and answers every one of the enabled uses with its deterministic fallback —
the precise silent-degradation failure the llm.uses validator at settings.py:273-285 was written
to prevent, reachable again through the model name. The only signal is a warning log and a metric
that never moves. It is also open-ended model identity on the operator's surface: the same image
can be pointed at any model string, and nothing records which model produced a stored summary,
relation or belief.

### database.pool_size and max_overflow have no bounds at all, and pool_size=0 means an unbounded pool in SQLAlchemy

`src/memory_service/config/settings.py:88` · config-openness

MEMORY__DATABASE__POOL_SIZE=0 is accepted and silently removes the connection ceiling
(pool_timeout then never fires), so a burst can open connections until Postgres refuses at
max_connections — a runtime 'too many clients' storm, not a startup error. A large value is
equally accepted and is multiplied by service.workers (3 by default) plus the worker container. In
the other direction, nothing stops pool_size+max_overflow from being set below
GRAPH.max_parked_traversals=8, at which point parked graph traversals can hold the entire pool and
starve the read path — a frozen constant whose safety argument depends on an env-overridable value
it does not match.

### The shipped compose pins MEMORY__BLOB__PROVIDER in `environment:`, so environment=prod can never start under it

`docker-compose.yml:18` · config-openness

An operator who sets MEMORY__SERVICE__ENVIRONMENT=prod in .env (the one place .env.example:37-39
tells them to set it) gets a container that crash-loops on a ValueError at startup, and no edit to
.env can fix it because compose overrides the field the validator objects to. Reaching a prod
configuration requires editing docker-compose.yml, which contradicts the stated goal of a plain
`docker compose up` whose only operator surface is .env.

### jwt mode is accepted in prod with no issuer and no audience pinned, disabling both checks

`src/memory_service/config/settings.py:125` · config-openness

A prod deployment passes the startup guard with mode=jwt and both claims unset, and then accepts
any token the configured JWKS endpoint can verify — including tokens the same identity provider
minted for a different audience or a different service. Classic audience confusion, reachable with
defaults and no warning. A missing jwks_url is also only discovered on the first request
(authentication.py:86-87), as a per-request AuthenticationFailed rather than a startup failure.

### Expansion fetches every chunk of every target node to use the first one, and a whole node to use two neighbours

`src/memory_service/modules/context/expansion.py:144` · context-hotpath

On every cache-missed /v1/context request over documents, Postgres ships and Python materialises
the full text of all chunks under all expansion targets plus all chunks of the seed nodes, when at
most 8 expansion items and 2 neighbours per seed can be used. For section-sized nodes this is tens
of kilobytes of chunk text and tens of `Chunk` objects per request, wasted. Both calls could be
`ORDER BY ordinal LIMIT`-shaped per node, or the neighbour lookup could ask for the two adjacent
ordinals directly.

### The same context-graph edge query is issued twice per request from two separate unit-of-work sessions

`src/memory_service/modules/context/evidence.py:241` · context-hotpath

Every cache-missed /v1/context request that has document chunks pays a second Postgres session for
rows it already has: `SqlUnitOfWork.__aenter__` creates a session, checks out a pooled connection
and issues BEGIN, constructs 13 repository objects (adapters/db/uow.py:98-116), and `__aexit__`
issues a ROLLBACK because nothing commits (:126-127). That is ~3 extra round trips plus a pool
checkout per request, on the connection pool the reads share, purely to re-derive a subset of
`edges`. Passing expansion's edge list (or the stage's cached result) to `required_groups` removes
the query entirely.

### candidate_to_item builds a ContextItem and EvidenceRef for every candidate, including ones only used as unused evidence

`src/memory_service/modules/context/builder.py:577` · context-hotpath

At the benchmark depth (final_k=100) `result.candidates` carries ~100 ranked items plus up to 8
expansions plus graph facts plus any ESCALATION candidates, while `memories_max` caps memories at
50 — so roughly half the ContextItem/EvidenceRef pairs are constructed, validated and thrown away,
along with one `datetime.now(UTC)` syscall each. Combined with the unbounded escalation fan-out
above, the count is not bounded by any depth knob at all. Building token estimates cheaply in the
selection loop and calling `candidate_to_item` only for items that are actually placed (plus
companions) removes the whole discarded half.

### abstractive_summaries issues up to 24 sequential LLM calls per document from inside the index job

`src/memory_service/modules/context/summaries.py:193` · ingest-path

With the `summaries` use enabled, each document.index job serialises up to 24 independent model
round trips before a single vector is upserted; the loop body reads only `by_id[nid]`,
`texts[nid]` and `summaries[nid]` and writes only `out[nid]`, so there is no cross-iteration
dependency at all. At a few seconds per call this adds a minute or more of pure wall clock per
document to a queue whose other work (embedding) is already the bottleneck. Gathering the 24
calls, or packing them the way chunking.situate_chunks packs its batches, collapses it to one or a
few round trips.

### situate_chunks awaits its LLM batches one after another in the document parse job

`src/memory_service/modules/ingestion/chunking.py:367` · ingest-path

The batching is correct but the batches run strictly in series: up to 6 model calls of 1024
max_tokens each, back to back, inside the document.parse job and before the transaction that
writes nodes/chunks/edges (ingestion/service.py:311-338). Each batch writes into disjoint indices
of `out` and reads nothing another batch produced, so the six awaits can be gathered, cutting that
stage from 6 x RTT to 1 x RTT and shortening the window in which the parse job holds its
`document:{id}` lock.

### reflect_all loads a global newest-1000 window, so busy tenants starve every other tenant out of reflection

`src/memory_service/modules/memory/reflection.py:90` · ingest-path

Once more than 1000 memories are created inside the 24h window across all tenants, the sweep sees
only the newest 1000: any tenant or principal whose memories fall outside that cut is never
reflected, and there is no cursor or resume -- the next sweep re-runs the same newest-first query
and makes the same cut, so the starvation is permanent, not delayed. Worse, `reflected_at` is
derived from the same truncated slice, so a scope whose prior reflection memory was cut off looks
unreflected and gets charged for another LLM call every sweep. Paging by (created_at, memory_id)
or sweeping per tenant fixes both; 1000 full CanonicalMemory rows also sit in the worker's heap at
once for a job that only needs 40 per principal (reflection.py:104).

### evict_working rewrites a working-memory list with one round trip per retained item, through a non-atomic delete

`src/memory_service/modules/memory/forgetting.py:209` · ingest-path

Two costs. Throughput: a key with N retained items costs N pipelined round trips to Dragonfly
instead of 1, for every key touched by every sweep, and the sweep walks all `wm:*` keys
(forgetting.py:184-187). Correctness: the list is deleted before it is rebuilt, so a concurrent
EphemeralMemory.remember RPUSH landing in that window (ephemeral.py:46, same key) is pushed onto
the empty key and then trimmed away by the sweep's `max_len=len(keep)`, silently losing a just-
written working memory; a crash anywhere between line 208 and the last push loses the entire list.
One variadic push after the delete narrows the window to a single command pair.

### ForgettingService.restore has no caller: archived memories can never be brought back

`src/memory_service/modules/memory/forgetting.py:143` · dead-code

Dead code whose absence is a behavioural gap: archiving is one-way in the running service.
modules/memory/forgetting.py:8 and modules/jobs/registry.py:143 both promise restorability, and
domain/enums.py:108 documents ARCHIVED as "forgotten by policy: kept, restorable, out of
retrieval". Once the periodic `periodic.memory_forget` job (jobs/registry.py:230-232) archives a
memory it is permanently out of retrieval, with no API or job able to reverse it.

### EvidenceRef.span_start, span_end and source_hash are never written by any producer and never read by any consumer, yet ship in the public API

`src/memory_service/domain/evidence.py:31` · dead-code

Three fields of the claim-level provenance contract are structurally always null for every client.
A caller reading the OpenAPI schema or the Python SDK sees documented character offsets and a

### Four enum members are produced at zero sites, three of them while API field descriptions tell clients to expect them

`src/memory_service/domain/enums.py:177` · dead-code

Clients branch on states the service can never emit. A caller polling /v1/jobs/{job_id} and
treating RETRYING as "keep waiting" versus FAILED as "give up" will misread every retrying job,
because a procrastinate job scheduled for another attempt comes back as PENDING. The SDK's error

### The graph-layer restriction feature is dead: LAYERS is unreferenced, the `layers` argument is threaded through five sites and is always None, and the module docstring describes two behaviours that do not exist

`src/memory_service/domain/graph.py:21` · dead-code

A dead constant plus dead parameter plumbing across five signatures in the port and both graph
adapters, and a docstring that will mislead the next person to touch graph retrieval into
believing causal-first ordering and per-layer filtering are implemented. The SQL branch in
neighborhood_query that consumes `layers` (postgres_store.py:105-113) has never run with a non-
None value, so it is untested in production and in the test suite.

### An HTTP route reaches past the repository port into the SQLAlchemy ORM and opens a raw session

`src/memory_service/api/routers/v1/conversation.py:268` · solid-coupling

Tenant scoping, which every repository method takes as its first argument, is reimplemented inline
as `row.tenant_id and row.tenant_id != ctx.tenant_id`. On a row whose tenant_id is NULL the left
operand is falsy, the whole condition is False, and the row is returned to any caller. No
application enqueue writes a NULL tenant today, but both the column and the JobSpec field permit
it, so the next tenant-less enqueue turns that row into cross-tenant readable data with no test or
type to stop it. Separately, any change to how outbox rows are stored now has to be made in the
ORM and in this route.

### BlobAlreadyExists is part of the BlobStore contract but lives in one concrete adapter, so a module imports that adapter to catch it

`src/memory_service/modules/ingestion/service.py:401` · solid-coupling

The exception that makes `if_generation_match=0` uploads idempotent is not in the port, so a new
BlobStore adapter (the SeaweedFS/S3 profile the port docstring anticipates) that raises its own
already-exists error falls into the `else: raise` branch. The archive segment is then marked
failed and wrapped as DependencyUnavailable (ingestion/service.py:410-413), so re-running an
archive job for bytes that are already in the store can never recover — the retry that should be a
no-op permanently fails the document.

### Three modules depend on a private constant inside the memory-intelligence module for their stop-word vocabulary

`src/memory_service/modules/context/evidence.py:28` · solid-coupling

There is no owner for the service's stop-word vocabulary. Editing native.py:44 to tune memory
extraction silently changes evidence-group term selection, summary keyword extraction and graph
entity filtering in three other modules at once, with nothing naming the dependency (the import is
of an underscore-private name, so no linter or architecture test flags it). Conversely, adding a
stop word to make retrieval ignore a filler term requires edits in four separate lists that
already disagree with each other — sparse.py stops "before/after/during/over/under", native.py
does not; lexical.py stops "who/what/when/where", native.py does not.

### documents.max_file_bytes (100 MB) can never take effect behind MAX_BODY_BYTES (25 MB)
